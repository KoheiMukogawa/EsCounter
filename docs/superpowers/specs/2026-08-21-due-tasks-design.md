# 設計：期限つき作業（due tasks）

日付：2026-08-21
対象：`index.html`
状態：設計確定・実装前

## 1. 解決する摩擦

選考が進むと、ES提出のあとに「適性検査の受験」「Webテスト」「動画提出」といった
**固定日時ではないが期限がある作業**が企業ごとに積み上がる。現在の ESM は企業に
`deadline`（ES提出期限）を1つしか持てないため、これらを置く場所がない。結果として
作業が企業からのメールに埋もれ、後回しにして落とす。

北極星の問い（「就活ワークフローの実在する摩擦を消すか？」）への答え：消す。
落とすと選考が終わる種類の取りこぼしであり、既存の企業ツリーの延長線上で解ける。

## 2. 非目標（明示的に作らないもの）

作らない理由を残しておく。あとから「なぜ無いのか」を再検討させないため。

- **面接など固定日時の予定**：カレンダーに任せる。日時・所要時間・場所を持ち始めると
  カレンダーアプリになり、原則1（集中を奪わない）と原則4（余計な機能を作らない）を壊す。
- **通知（プッシュ/メール/ブラウザ通知）**：ESM は開かないと見えない。これは受け入れる。
  常駐して注意を引く仕組みは、作者がこのアプリを作った動機そのものと衝突する。
- **カレンダービュー（月表示・週表示）**：一覧は「期限が近い順のリスト」で足りる。
- **企業に紐づかないタスク**（合同説明会、OB訪問など）：YAGNI。必要になってから。
- **タスクのテンプレート／候補サジェスト**：自由入力で足りる。

## 3. データモデル

企業オブジェクトに配列を1つ追加する。

```js
c.tasks = [ { id, name, due, done } ]
```

- `id`  : `genId()`（既存、`index.html:712`）
- `name`: 自由入力の文字列（例：「適性検査」「動画提出」）
- `due` : `'YYYY-MM-DD'`。既存 `c.deadline` と同じ形式・同じ `<input type="date">`。
          **必須**（「期限つき作業」なので期限のないタスクは持たない）。時刻は持たない。
- `done`: boolean

### 既存 `deadline` は据え置く

`c.deadline` / `c.submitted` / `c.result` は**一切変更しない**。

`submitted` は結果バッジ（通過/結果待/落選）とツリーのソート順（`index.html:941-948`）の
前提になっており、これを `tasks` に溶かすと3箇所の同時書き換えとデータ移行が必要になる。
概念の統一は**ビュー層だけ**で行う（§4.1）。データ移行ゼロ、既存ロジックの破壊リスクゼロ。

### 永続化は無変更

Firestore 保存もローカル5世代バックアップ（`index.html:768`）も `companies` を丸ごと
シリアライズしているため、`tasks` は自動的に保存・復元される。保存系のコードは触らない。

### 後方互換

既存データの企業には `tasks` が存在しない。読み出しは必ず `(c.tasks||[])` で行う。
マイグレーション処理は書かない（存在しない＝空、で意味が通るため）。

## 4. UI

### 4.1 気づく場所：サイドバー最上部「期限が近い」ブロック

`.sidebar` の中、`.sidebar-header`（企業）より**上**に新設する。

```
┌─サイドバー─────────┐
│ ⚠ 期限が近い          │  ← 該当0件なら DOM ごと消える
│  JAL 適性検査   今日！│
│  ANA Webテスト   残2日│
│  三菱 動画提出    残3日│
├──────────────────┤
│ 企業                ＋ │
│ ▼ JAL自社養成  残3日 2/5│
└──────────────────┘
```

**載せる条件**：全企業の未完了項目のうち、`deadlineState()` 換算で**期限切れ、または残り7日以内**のもの。

**並び順**：`due` 昇順（期限切れが最上部）。

**件数**：最大5件。超過分は末尾に「他 n 件」とだけ出す（リンクにしない）。

**0件のとき**：ブロックごと出さない。平常時はサイドバーの見た目が現状から一切変わらない。
「足したと気づかないくらい」を満たす。

**ES提出期限の合成**：`c.deadline` があり `c.submitted` が false の企業は、
このリストを組むときだけ仮想項目 `{name:'ES提出', due:c.deadline}` として合成する。
データは作らない。これによりユーザーからは「ES提出も適性検査も同じ1本のリスト」に見える。

**行の操作**：
- 行クリック → `activeCompanyId` をその企業にして `render()`（＝企業へジャンプ）
- チェック → 完了。通常タスクは `t.done=true`。**ES提出の仮想行だけは `c.submitted=true` を立てる**
  （既存の `cbarSubmit` と同じ挙動。`index.html:1103-1107`）

**残り日数の表示**：既存 `deadlineState()`（`index.html:923-935`）をそのまま流用する。
`今日！` / `残n日` / `期限切` と `danger` / `warn` / `done` のクラスが既にあるので、
色と文言の体系は企業ツリーのバッジと一致する。新しい表現を発明しない。

### 4.2 追加・編集する場所：企業情報モーダル

既存の「企業を追加 / 企業情報を編集」モーダル（`index.html:500-530`）の
「提出期限」フィールドの**下**に、作業の増減リストを足す。

```
提出期限   [2026-09-01]

期限つき作業
  ☑ [適性検査      ] [2026-08-25] [×]
  ☐ [動画提出      ] [2026-09-03] [×]
  ＋ 作業を追加
```

- 各行 = 完了チェック ＋ 名前 `<input type="text">` ＋ 期限 `<input type="date">` ＋ 削除 `×`
- 「＋ 作業を追加」で空行を1つ足す（チェックは外れた状態）
- 保存時、**名前が空、または期限が空の行は捨てる**（バリデーションエラーは出さない）
- 完了済みタスクもこのリストに出す。完了したものを見返して消せる場所がここしかないため。
  §4.1 の一覧は未完了だけを載せるので、完了タスクに触れるのはここだけになる。

サイドバーには常設UIを増やさない。追加はモーダル、完了は一覧から1クリック、という分担。

### 4.3 企業ツリーのバッジは変更しない

ツリーの残り日数バッジは現状どおり `c.deadline`（ES提出期限）を表示する。
§4.1 で取りこぼしは解消済みであり、ここを触ると変更範囲がソート順まで波及する。YAGNI。

## 5. 併せて直す既存バグ

`openAddCompanyModal()`（`index.html:1715`）は `dataset.editId` を削除しない。
一方 Escape ハンドラ（`index.html:1801`）は `open` クラスを外すだけで `editId` を残す。

再現手順：
1. 企業Xを「企業情報を編集」で開く → `dataset.editId = X`
2. Escape で閉じる → `editId` は残ったまま
3. サイドバーの ＋ で新規追加を開く → フィールドは空になるが `editId` は X のまま
4. 企業名を入れて保存 → `confirmAddCompany()` が編集経路に入り、
   **企業Xの名前・URL・ログインID・提出期限が入力値で上書きされる**

原則2（データを失わない）に直接抵触する。今回タスク配列を同じモーダルに載せると
同じ経路で `tasks` も消えるため、この設計に含める。

修正：`openAddCompanyModal()` の先頭で `delete bg.dataset.editId` し、
モーダル見出しとボタン文言も新規用にリセットする。

## 7. 検証

このリポジトリにテスト基盤はない（バニラ、ビルド工程なし）ため自動テストは書かない。
`python3 -m http.server 8000 --directory .` → http://localhost:8000/ で以下を手動確認する。

1. 既存データ（`tasks` を持たない企業）を開いてもエラーが出ず、表示が現状と変わらない
2. 企業に作業を2件追加 → リロード後も残っている（Firestore往復）
3. 期限を今日／2日後／10日後にした3件で、10日後だけがサイドバーに出ない
4. 全件完了 or 全件8日以上先 → 「期限が近い」ブロックが消える
5. 一覧のチェックで完了 → ブロックから消え、モーダルには完了済みとして残る
6. ES提出の仮想行にチェック → 企業操作バーが「✓ 提出済み」に変わる
7. §5 の再現手順をなぞり、企業Xが上書きされないこと
8. 企業を削除しても他企業の一覧が壊れないこと
9. ダークテーマで色が破綻しないこと

## 8. リスク

- **サイドバーの圧迫**：上限5件＋0件時に消える設計で抑える。それでも狭ければ
  しきい値を7日→3日に絞る（数値定数を1箇所に置いて変えやすくする）。
- **ES提出の二重表示**：ES提出期限がサイドバー上部と企業ツリーのバッジの両方に出る。
  意図的。上部は「横断で迫っているもの」、ツリーは「その企業の状態」で役割が違う。
  実際に使ってうるさければ上部からES提出の合成を外す（§4.1 の合成をやめるだけで済む）。
