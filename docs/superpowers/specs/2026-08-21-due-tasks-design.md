# 設計：期限つき作業（due tasks）と選考順ソート

日付：2026-08-21（改訂2）
対象：`index.html`
状態：設計確定・実装前

## 1. 解決する摩擦

選考が進むと、ES提出のあとに「ウェブテスト」「適性検査」「動画提出」といった
**固定日時ではないが期限がある作業**が企業ごとに積み上がる。現在の ESM は企業に
`deadline`（ES提出期限）を1つしか持てないため、これらを置く場所がない。結果として
作業が企業からのメールに埋もれ、後回しにして落とす。

さらに、**現在の並び順は「ES提出＝その企業は一段落」という誤った前提**で書かれている
（`index.html:941-948`）。実際は ES提出は次フェーズの開始であり、一番動きのある企業が
一番下に沈む。本設計はこの前提ごと直す。

北極星の問い（「就活ワークフローの実在する摩擦を消すか？」）への答え：消す。
落とすと選考が終わる種類の取りこぼしであり、既存の企業ツリーの延長線上で解ける。

## 2. 非目標（明示的に作らないもの）

作らない理由を残す。あとから「なぜ無いのか」を再検討させないため。

- **面接など固定日時の予定**：カレンダーに任せる。日時・所要時間・場所を持ち始めると
  カレンダーアプリになり、原則1（集中を奪わない）と原則4（余計な機能を作らない）を壊す。
- **通知（プッシュ/メール/ブラウザ通知）**：ESM は開かないと見えない。これは受け入れる。
  常駐して注意を引く仕組みは、作者がこのアプリを作った動機そのものと衝突する。
- **カレンダービュー（月表示・週表示）**：期限順に並ぶツリーで足りる。
- **サイドバー上部の横断リスト**：改訂1では作る予定だった。ツリー自体が期限順に並び
  作業名を表示するようになったため、同じ情報が2か所に出る重複になる。**不採用**。
  足すのは安く、あとから戻せる（§8）。
- **企業に紐づかないタスク**（合同説明会、OB訪問など）：YAGNI。
- **ウェブテスト専用フィールド**：ウェブテストは汎用タスクの一例として扱う。
  専用フィールドを作ると適性検査・動画提出・GDの置き場所がなくなる。
- **タスクのテンプレート／候補チップ**：自由入力で足りる。
- **時刻**：受験期限は「この日まで」なので日付で足りる。既存 `deadlineState()` をそのまま使える。

## 3. データモデル

企業オブジェクトに配列を1つ追加する。

```js
c.tasks = [ { id, name, due, done } ]
```

- `id`  : `genId()`（既存、`index.html:712`）
- `name`: 自由入力の文字列（例：「ウェブテスト」「動画提出」）
- `due` : `'YYYY-MM-DD'`。既存 `c.deadline` と同じ形式・同じ `<input type="date">`。
          **必須**（「期限つき作業」なので期限のないタスクは持たない）。時刻は持たない。
          この形式は辞書順比較がそのまま日付順になるため、ソートに文字列比較を使える。
- `done`: boolean

### 既存 `deadline` は据え置く

`c.deadline` / `c.submitted` / `c.result` のフィールドは**変更しない**（ソートと
バッジの解釈は変わるが、データの意味と書き込み経路は現状のまま）。

`submitted` は結果バッジと企業操作バーの前提になっており、これを `tasks` に溶かすと
データ移行が必要になる。概念の統一は**ビュー層だけ**で行う（§4.1）。

### 永続化は無変更

Firestore 保存もローカル5世代バックアップ（`index.html:768`）も `companies` を丸ごと
シリアライズしているため、`tasks` は自動的に保存・復元される。保存系のコードは触らない。

### 後方互換

既存データの企業には `tasks` が存在しない。読み出しは必ず `(c.tasks||[])` で行う。
マイグレーション処理は書かない（存在しない＝空、で意味が通るため）。

## 4. UI

### 4.1 中核：`nextDue(c)` — その企業の「次にやること」

ツリーの並び順・バッジ・2行目のすべてがこの1つの関数から導出される。

```js
function nextDue(c){
  const items=[];
  if(c.deadline && !c.submitted) items.push({name:'ES提出', due:c.deadline, kind:'es'});
  (c.tasks||[]).forEach(t=>{ if(!t.done && t.due) items.push({name:t.name, due:t.due, kind:'task'}); });
  if(!items.length) return null;
  items.sort((a,b)=> a.due<b.due ? -1 : a.due>b.due ? 1 : 0);
  return items[0];
}
```

ES提出期限は**データを作らず、ここで仮想の1件として合成する**。これによりユーザーからは
「ES提出もウェブテストも同じ1本の流れ」に見えるが、内部のデータ構造は増えない。

### 4.2 並び順（既存 `sortRank` を置き換える）

```
rank 2 : c.submitted && c.result==='fail'      … 落選（最下段）
rank 0 : nextDue(c) !== null                    … 次にやることがある（最上段）
rank 1 : それ以外                                … 結果待ち・通過・提出済みで残作業なし
```

落選判定を最初に行う（落選企業に未完了タスクが残っていても最下段へ沈める）。

同ランク内：
- rank 0 は `nextDue().due` の**昇順**。期限切れが最上部に来る。
- 同じ `due`、および rank 1 / 2 は `companies.indexOf` （配列の並び＝挿入順）で安定化。

```
▶ 三菱商事    今日！ 0/3
    適性検査
▶ ANA        残1日 3/3
    ウェブテスト
▼ JAL自社養成  残8日 2/5
    ES提出
   設問1
   設問2
▶ トヨタ     結果待ち
```

### 4.3 ドラッグによる企業の並べ替えを削除する

並び順が状態から完全に導出されるため、企業行のドラッグ並べ替え（`index.html:995-1009`）は
効かなくなる。掴んで動かせるのに何も起きない状態は壊れて見えるので、
`row.draggable` と dragstart / dragend / dragover / dragleave / drop の各リスナー、および
`.ctree-co.dragging` / `.ctree-co.drag-over` の CSS を削除する。

**設問（`.ctree-q`）のドラッグ並べ替えは別物であり、触らない。**

副作用として、落選・結果待ちの企業を手で並べ替える手段がなくなる。挿入順のままになる。
これは受け入れる（それらの企業は能動的に触る対象ではない）。

### 4.4 企業行の表示（2行構成）

行の DOM を1段だけ変える。現在は `caret / name / badge / prog / close` がフラットに
並んでいるが、name を包む縦積みのラッパーを挟む。

```
.ctree-co (flex, align-items:center)
  ├ .ctree-caret
  ├ .ctree-co-body   ← 新規。flex:1; min-width:0; flex-direction:column
  │   ├ .ctree-co-name   ← flex:1 を外す（幅はラッパーが持つ）
  │   └ .ctree-co-sub    ← 新規。次にやることの名前
  ├ .ctree-badge
  ├ .ctree-prog
  └ .ctree-close
```

`.ctree-co-sub` は既存の `.ctree-q-meta`（`index.html:178`）と同じ語彙で書く：
`font-size:10px; color:var(--text3); font-family:'DM Mono',monospace; margin-top:1px;`
＋ `white-space:nowrap; overflow:hidden; text-overflow:ellipsis;`

`nextDue(c)` が null の行には `.ctree-co-sub` を**生成しない**ので、結果待ち・落選の行は
今と同じ1行の高さのままになる。

`.ctree-co-name` は active 企業で contentEditable になる（`index.html:962-969`）。
ラッパーを挟んでもこの挙動は変わらない。

**`submitted` クラスの付与条件を変える。** 現在は `c.submitted` だけで行に `.submitted` が
付き（`index.html:956`）、`.ctree-co.submitted .ctree-co-name` が企業名を薄くする
（`index.html:154`）。新しいモデルでは提出済み＝一段落ではないため、このままだと
ウェブテストが明日に迫った企業が最上部に**薄い文字で**並ぶことになり、本設計の目的を
自分で打ち消す。付与条件を `c.submitted && !nextDue(c)` に変える
（＝本当にやることが無い企業だけを薄くする）。CSS は変更しない。

### 4.5 バッジの優先順位

```
1. c.submitted && c.result==='fail'  → 「落選」      (.fail)
2. nextDue(c) あり                    → deadlineState(due) の label / cls  (.dl)
3. c.submitted && c.result            → 「通過」/「結果待」  (.pass / .pending)
4. c.submitted                        → 「提出済」    (.submitted)
5. それ以外                            → バッジなし
```

現行との違いは **2 が 3・4 より優先される**こと。ES提出済みでもウェブテストが残っていれば
「提出済」ではなく「ウェブテスト / 残1日」が出る。これが今回の変更の要点。

残り日数は既存 `deadlineState()`（`index.html:923-935`）をそのまま使う。
`今日！` / `残n日` / `期限切` と `danger` / `warn` / `done` のクラスが既にあるので、
色と文言の体系は現状と一致する。新しい表現を発明しない。

### 4.6 追加・編集する場所：企業情報モーダル

既存の「企業を追加 / 企業情報を編集」モーダル（`index.html:519-522`）の
「提出期限」フィールドの**下**に、作業の増減リストを足す。

```
提出期限   [2026-09-01]

期限つき作業
  ☑ [ウェブテスト   ] [2026-08-25] [×]
  ☐ [動画提出      ] [2026-09-03] [×]
  ＋ 作業を追加
```

- 各行 = 完了チェック ＋ 名前 `<input type="text">` ＋ 期限 `<input type="date">` ＋ 削除 `×`
- 「＋ 作業を追加」で空行を1つ足す（チェックは外れた状態）
- 保存時、**名前が空、または期限が空の行は捨てる**（バリデーションエラーは出さない）
- 完了済みタスクもこのリストに出す。ツリーは未完了しか見せないので、
  完了したものを見返して消せる場所はここだけになる。

サイドバーには常設UIを増やさない。追加はモーダル、状態はツリー、という分担。

## 5. 併せて直す既存バグ

`openAddCompanyModal()`（`index.html:1715`）は `dataset.editId` を削除しない。
一方 Escape ハンドラ（`index.html:1801`）は `open` クラスを外すだけで `editId` を残す。

再現手順：
1. 企業Xを「企業情報を編集」で開く → `dataset.editId = X`
2. Escape で閉じる → `editId` は残ったまま
3. サイドバーの ＋ で新規追加を開く → フィールドは空になるが `editId` は X のまま
4. 企業名を入れて保存 → `confirmAddCompany()` が編集経路に入り、
   **企業Xの名前・URL・ログインID・提出期限が入力値で上書きされる**

原則2（データを失わない）に直接抵触する。今回タスク配列を同じモーダルに載せると
同じ経路で `tasks` も消えるため、この設計に含める。

修正：`openAddCompanyModal()` の先頭で `delete bg.dataset.editId` し、
モーダル見出しとボタン文言も新規用にリセットする。

## 7. 検証

このリポジトリにテスト基盤はない（バニラ、ビルド工程なし）ため自動テストは書かない。
`python3 -m http.server 8000 --directory .` → http://localhost:8000/ で手動確認する。

1. 既存データ（`tasks` を持たない企業）を開いてもエラーが出ず、並びとバッジが破綻しない
2. 企業に作業を2件追加 → リロード後も残っている（Firestore往復）
3. **ES提出済み＋ウェブテスト未完了**の企業が、未提出企業より上（期限が近ければ）に来る
   ＝ 今回の変更の主目的。改修前は最下段に沈んでいたこと
4. 期限を今日／1日後／10日後にした3社が、その順に上から並ぶ
5. 期限切れ（昨日）の作業を持つ企業が最上部に「期限切」で出る
6. 全作業を完了 → その企業が rank 1 に落ち、2行目が消えて1行の高さに戻る
7. 落選にした企業は、未完了作業が残っていても最下段に沈む
8. **ES提出済み＋ウェブテスト未完了**の企業の名前が薄くならない（§4.4 の `submitted`
   クラス条件）。全作業を完了させると薄くなる
9. 企業名が長いとき（例：三菱UFJモルガン・スタンレー証券）に2行目が崩れない・
   企業名が省略記号で切れる
10. 企業行をドラッグしても何も起きない（掴めない）／設問のドラッグ並べ替えは今までどおり動く
11. §5 の再現手順をなぞり、企業Xが上書きされないこと
12. ダークテーマで2行目の色が破綻しないこと

## 8. リスク

- **手動並べ替えの喪失**：企業の並びが完全に自動になる。承知の上での選択。
  戻すなら `.ctree-q` のドラッグ実装を企業行に複製すればよい（削除前のコードは git 履歴に残る）。
- **サイドバーが縦に伸びる**：未完了作業を持つ企業が増えるほど2行の行が増える。
  `.company-tree` は `overflow-y:auto`（`index.html:144`）なのでスクロールで吸収される。
  それでも窮屈なら、2行目を active 企業と期限3日以内の企業だけに絞る。
- **選択中の企業が勝手に動く**：期限順ソートなので、作業を完了した瞬間に選択中の企業が
  リスト内で下へ移動する。違和感が強ければ、選択中の企業だけ位置を固定する例外を足す。
  まずは例外なしで使ってみる。
